# 第四题（选做）简短说明（Redis Pipeline 与性能比较）

个人参数：N = 1000+100C+S = **1010**，Q = **100** → 批次数 `ceil(1010/100)=11`，最后一批 **10** 条。

## 实现
- **方案甲（逐条写入）**：`for i in 1..N: r.set("exam:12403030110:seq:<i>", "value-12403030110-<i>")`，每条 `SET` 同步等待返回后才发下一条，不使用 Pipeline/多线程/异步。
- **方案乙（普通 Pipeline）**：每批 `Q=100` 条，`r.pipeline(transaction=False)` 批量 `SET` 键 `exam:12403030110:pipe:<i>`，`execute()` 取得整批回复后再提交下一批；末批 `range` 用 `min(start+Q-1, N)` 截断，正确处理 10 条尾批。
- **计时**：`time.perf_counter()` 覆盖命令构造、发送、回复接收全过程；Pipeline 在最后一批 `execute()` 返回后才停止计时。共 3 轮，取平均值。

## 实测数据
| 指标 | 实测值 |
|---|---|
| 命令总数 | 1010 |
| Pipeline 批次数 | 11 |
| 最后一批数量 | 10 |
| 方案甲耗时(ms) | 248.04（223.50 / 243.86 / 276.77） |
| 方案乙耗时(ms) | 23.20（22.32 / 22.91 / 24.37） |
| 加速比 | 约 10.7 倍 |

完整性核验：方案甲键数 1010、方案乙键数 1010，抽样键 1、100、101、1010 的值全部正确，尾批第 1010 条 `value-12403030110-1010` 已写入。

## 结论
Pipeline 更快：方案甲 1010 条命令 = 1010 次完整往返（每条约一次 RTT）；方案乙把命令合并为 11 批，只在批末等待回复，往返次数从 1010 降到 11。

若差异不明显甚至 Pipeline 更慢，可能原因：① 客户端与服务端同机，单次 RTT 极短，节省的往返被命令构造与结果解析开销摊薄；② 数据量小（1010 条、值很短），总耗时仅毫秒级，测量噪声占比大；③ 集群模式下 Pipeline 要按槽位拆分到不同节点，客户端需额外的分组与结果聚合开销；④ 服务端单线程处理，大批命令排队执行，吞吐提升但端到端时延不一定线性下降；⑤ 首次建连、连接池扩容、GC 等一次性开销影响单次测量。
